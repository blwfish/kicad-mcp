# SPEC: Placement Locus

**Status:** DRAFT — written 2026-05-31. Cold-reviewed same day; all blockers resolved. **Sequencing: this phase lands FIRST**, before the part-resolution work (`SPEC_Firmware_Part_Resolution.md`, now parked behind it) — locus is a foundational intent-model axis that changes what "place a resolved part" means.

---

## 1. Problem

The front end has silently assumed, since the beginning of the pipeline, that **every firmware-named device is a component placed on the board.** That is wrong for a large and common class of devices that are wired in from off-board:

| Device (audio-node) | Reality | Current (wrong) behavior |
|---|---|---|
| INMP441 mic | **remote** — positioned for acoustics, wired in | placed as a chip (and has no KiCad symbol — see part-resolution spec) |
| LD2410 presence | **remote** — needs line-of-sight | placed as a header module |
| Piezos | **remote** — mounted elsewhere | n/a / would be placed |
| Speakers | **remote** load | partially: a hardcoded speaker header |
| MAX98357A amps | **on-board, remote speaker I/O** | placed (correct), speaker header hardcoded |
| ESP32 / LDO / USB / caps / Rs | on-board | placed (correct) |

For the audio-node, **most of the interesting peripherals are remote** — the board is an MCU + amp + power core ringed by screw terminals. The model cannot express this. What exists are three disconnected fragments that each realize a connector a different way (§4), with no first-class concept.

## 3. Concept: placement locus (a fourth axis)

Alongside **identity** (firmware) / **footprint** / **availability**, a device has a **placement locus** — *where it physically lives relative to the board*:

- **`on_board`** — place the component's symbol/footprint (current behavior; the default).
- **`remote`** — do **not** place the device. Synthesize a **terminal/connector** with one position per boundary-crossing signal, redirect all the device's nets to it, document the device off-board, and **suppress its on-board support glue** (a remote mic's bypass cap and CHIPEN strap live at the device, not on this board).
- **`on_board_with_remote_io`** — place the chip normally, but redirect its **external-load** nets (declared in `board.yaml`, see §6) to a terminal.

Locus is a **board-level decision** — firmware cannot know whether a mic is reflowed or hangs on 18″ of wire — so it is **not firmware-derived**. It is set in `board.yaml` (§6). A card MAY carry a suggested default (an LD2410 is almost always remote), but the suggestion is surfaced as a **disclosed assumption**, never silently applied (consistent with the honest-by-construction contract). **Open Decision 1** settles how aggressive defaults may be.

## 4. The model gap, and unifying the three fragments

There is **no `Connector` dataclass**. A connector is just a `Peripheral` (`type="HDR"`, `origin="template"` for templates; `type="CONN"`, `origin="user"` for sidecar). Three "place a connector + route nets to it" operations exist via **three different code paths** — exactly the single-source-of-truth violation the project's Syntactic-Semantic Seam rule warns about:

| Fragment | Identity source | Materialized at | `origin` | Pin→net | Ref allocation |
|---|---|---|---|---|---|
| (a) `module:true` cards (MPU6050/OLED) | device-card YAML | import (`build_intent`) | `imported` | role-map by number | n/a (from card) |
| (b) `i2s_output_amps` speaker headers | `HDR_1X2` Python const | expand (template) | `template` | hardcoded `"1"`/`"2"` | `RefAllocator.next("J")` |
| (c) `board.yaml extra_connectors` | board.yaml | sidecar (`apply_sidecar`) | `user` | explicit dict | `_normalize_ref` |

**This spec introduces ONE terminal-synthesis helper** `synthesize_connector(crossing_signals, connector_type) -> (Peripheral, [Net edits], ConnectorLegend)` that handles the structural mechanics shared by all three: picks the symbol (`Screw_Terminal_01x{N}` / `Conn_01x{N}`) sized to N signals, allocates a collision-free ref through **one** allocator, redirects the named nets to numbered positions, labels each position from the signal/role name, and **validates N against the symbol pin count** (a check none of the three fragments do today — a latent bug).

**What the consolidation unifies (structural mechanics):** ref allocation, symbol sizing, pin-count validation, net endpoint retargeting, legend metadata emission.

**What it does NOT conflate:** Fragment (a) uses `Conn_01xN` (carrier-board socket for a module physically mounted on the board, `on_board` semantics); the new locus realizations use `Screw_Terminal_01xN` (screw terminals for field wiring to a remote device). The symbol/footprint selection remains distinct — `synthesize_connector` takes `connector_type` as a parameter. Fragments (a)/(b)/(c) are refactored to share the structural mechanics, but fragment (a)'s `Conn_01xN` semantics are unchanged.

## 5. Data model

```python
@dataclass
class Peripheral:
    ...
    locus: str = "on_board"     # NEW: on_board | remote | on_board_with_remote_io

@dataclass
class ConnectorLegend:
    """Per-connector silk legend metadata, populated by synthesize_connector, consumed by pcb_pipeline."""
    ref: str                 # e.g. "J3" — identifies the footprint in the placed PCB
    positions: list[str]     # positions[i] = signal name for pad number (i+1)
    device: str              # e.g. "INMP441" — set as the footprint value/description
```

`DesignIntent` gains a new field `connector_legends: list[ConnectorLegend] = field(default_factory=list)`. This field is populated by `synthesize_connector` and serialized with the intent YAML. `pcb_pipeline.py` consumes it in a new `_step_silkscreen_legends` step (see §7.1).

- `SCHEMA_VERSION` bump; `from_dict`/`_only_fields` back-compat (old docs default `locus="on_board"`, preserving current behavior; missing `connector_legends` defaults to `[]`).
- **Power net semantics for `remote`:** "power is delivered over the wire" means the remote device's VDD/GND pins are mapped to terminal positions — the terminal provides a tap onto the board's existing +3V3/GND rails (those rails exist from the power_tree template and are not removed). A remote INMP441 does not eliminate +3V3 from the board; it adds a terminal pin that taps +3V3 at the field-wiring point. This is an ADDED `Endpoint` on the existing power net, not a retarget away from the board rail.
- For `on_board_with_remote_io`: the `external_io` roles are declared in `board.yaml` per device type (see §6) — not in the device card. This avoids requiring MAX98357A (currently Python in `templates.py`) to be migrated to a YAML card for L3. Card-declared `external_io` remains the eventual target once MAX98357A is a device card, but board.yaml-declared is the initial implementation.
- No new `Net` field is required: crossing is realized by moving/adding `Endpoint`s onto the synthesized terminal (the net name is unchanged). A synthesized terminal carries `origin="template"` (re-generated each expand; the decision lives in `board.yaml`, re-applied each run — see §2 for verified `merge()` semantics).

## 6. `board.yaml` — the locus channel

```yaml
placement:
  INMP441:                 # keyed by device type (Open Decision 3: type vs ref)
    locus: remote
    connector: screw_terminal      # default for remote; or pin_header | pluggable
    # footprint omitted → uses series default (§2 pattern, N auto-sized)
  LD2410:
    locus: remote
  MAX98357A:
    locus: on_board_with_remote_io   # speaker leads to a terminal; chip stays on board
    external_io: [outp, outn]        # roles whose nets cross to the terminal
```

- Applied in `apply_sidecar` (after `build_intent`, before expand) — same insertion point as `extra_connectors`, now routing through the unified §4 helper.
- **Default screw-terminal footprint (Open Decision 4 — CLOSED):** Phoenix MKDS-1,5 series, 5.08 mm pitch. Pattern: `TerminalBlock_Phoenix:TerminalBlock_Phoenix_MKDS-1,5-{N}-5.08_1x{N:02d}_P5.08mm_Horizontal` where N is the signal count. Confirmed present in KiCad 10 for N = 2..16. Not verified on KiCad 9 (not installed); the series predates it. Re-verify on KiCad 9 before L2 and record the result in §2. Overridable per device via `footprint:` in `board.yaml`.
- **`external_io` for `on_board_with_remote_io`** is board.yaml-declared (not card-declared) for the initial implementation. The roles name signals on the device whose nets cross to the terminal (e.g. `[outp, outn]` for MAX98357A speaker outputs).
- Validation: `locus` ∈ the three values; `connector`/`footprint` against known sets; `external_io` roles against the device's known roles (from card or knowledge.py); device key against recognized types.

## 7. Realization in `generate.py`

The placement loop (`generate.py:46–73`, where `to_place` is built) and wiring loop (`112–129`, `for net in intent.nets:`) gain a locus branch **before** `to_place` is built:

- **on_board** → unchanged.
- **remote** → device excluded from `to_place`; synthesize terminal via §4 helper; the device's **signal** net endpoints are retargeted to the terminal (power/GND endpoints add a terminal tap, see §5); emit a `Gap(kind="remote_device", detail="INMP441 (mic): remote — wired to J3 (5-pos screw terminal); sourced off-board", resolved=True)`; **suppress the device's support-glue** (templates check `locus` before emitting decoupling/straps for that device).
- **on_board_with_remote_io** → device placed normally; the `external_io` nets retargeted to a synthesized terminal (generalizes the hardcoded speaker header in `i2s_output_amps`).

`Peripheral` needs no changes beyond the `locus` field. The wiring loop's existing guard at **line 114** (`if ep.ref not in placed: unresolved.append(...); continue`) naturally skips endpoints for refs not in `placed` — a remote device's symbol is never added to `placed`, so its original endpoints are silently dropped and only the terminal endpoints (which ARE in `placed`) are wired. This is the retargeting mechanism; no additional hook is required.

### 7.1 Silkscreen legend (functional wiring documentation — NOT cosmetic)

A field-wired terminal with no per-position labels is a wiring hazard: the silk legend **is** the wiring documentation for every remote device. So a synthesized connector is **not complete without its legend** — this is a hard requirement of the realization.

**Metadata flow (two-stage):**

1. **Schematic stage** — `synthesize_connector` populates a `ConnectorLegend` (§5) and appends it to `intent.connector_legends`. No pad coordinates yet — the PCB hasn't been created.

2. **PCB stage** — `pcb_pipeline.py` gains a new step `_step_silkscreen_legends`, running **after** `_step_place_footprints` (footprints are placed → pad coords are available). For each `ConnectorLegend` in `intent.connector_legends`:
   - Get pad positions for `legend.ref` via pcbnew (same API used in `pcb_keepout.py` / `pcb_autoroute.py`).
   - For pad number `i` (1-indexed): add silk text `legend.positions[i-1]` at a fixed offset above the pad center (offset TBD in L7, based on footprint pitch; 2mm above is a reasonable starting point for 5.08mm MKDS).
   - Set the footprint's value property to `legend.device` (e.g. `"INMP441"`).
   - After all labels placed, call `_op_check_silkscreen_overlaps` + `_op_auto_fix_silkscreen` on the full board (existing machinery).

Because `ConnectorLegend` is emitted by the **unified** `synthesize_connector` helper, every connector — remote terminals, speaker terminals, `extra_connectors` — gets a consistent legend automatically. Label text convention: short signal/role name (`SCK`, `+3V3`, `L+`), uniquified within the connector (two `GND` positions → `GND`/`GND` is fine; two different nets must not collide to the same short name). Full net name is implied by the device-identity value on the terminal.

## 9. Interaction with the part-resolution phase (A+C)

Locus runs **upstream** of part placement, and it changes A+C materially:

- A **remote** device still resolves its **identity** (INMP441 — for terminal labels + BOM doc) but **availability is moot**: no chip is placed, so **workstream A (authoring the INMP441 chip symbol/footprint) is NOT needed** for the audio-node. A shrinks to "only if a device is ever `on_board`."
- Locus **dissolves the resolved-but-unplaceable problem (cold-review I3/G2) for the remote-device subset**: a device with no KiCad symbol that is also `remote` is realized as a terminal, never an unplaceable chip. On-board devices with no KiCad symbol remain unresolved and remain in scope for the part-resolution phase — locus does not shrink that problem.
- The part-resolution "place a resolved part" logic must consult `locus` first: `on_board` → place symbol (needs availability); `remote` → terminal; `on_board_with_remote_io` → both.

## 11. Open decisions (for the cold reviewer)

1. **Locus default aggressiveness** — card may *suggest* a default locus (LD2410 → remote) with a disclosed assumption, OR locus is always board.yaml-explicit and an un-specified device defaults `on_board` (current behavior, safe but means every remote device needs a board.yaml line). Given the project's "never silently assume" stance, recommend: **no silent remote default; `on_board` default + a `placement_unspecified` advisory gap listing devices that are *commonly* remote**, prompting the user to set them.
2. **Synthesized-terminal `origin`** — RESOLVED: `template` (re-generated each expand, decision in board.yaml). Verified in §2: `merge()` drops template-origin items, re-synthesized fresh each run. No duplication/orphaning.
3. **board.yaml `placement` key: device type vs device ref** — type is reusable and matches how loci actually generalize (all INMP441s are remote); ref is needed only to split multi-instance same-type devices to different loci. Recommend type-keyed with optional ref override.
4. **Default terminal-block footprint** — CLOSED: Phoenix MKDS-1,5, 5.08 mm, auto-sized to N. Full pattern in §6. Re-verify on KiCad 9 at L2 start.
5. **`external_io` source for `on_board_with_remote_io`** — RESOLVED for initial implementation: board.yaml-declared (no MAX98357A card migration required for L3). Card-declared is the eventual target.
6. **Silk label text convention (§7.1)** — RESOLVED: short signal/role name, uniquified per connector, full net implied by footprint value. Dedup rule: two `GND` positions → both labeled `GND`; two DIFFERENT nets must not collide to the same short name (use full role name as tiebreaker).
